# AGENTS.md for Tests

## General Rules

- Please do not use mocking frameworks like Moq or NSubstitute for test doubles, use hand-crafted test doubles instead.
- Do not write nested test classes. All tests should reside in a class which is directly placed in a namespace.
- Use FluentAssertions instead of xunit's `Assert` class.
- Prefer Sociable Tests instead of Solitary Tests. Create as much test coverage as possible by calling higher level production APIs. Only write solitary tests to cover lower level APIs that are hard to test with Sociable Tests.
- Keep test coverage at least above 90%.
- `dotnet test --solution BrilliantMessaging.slnx --no-build` currently forwards `--report-trx`, which the xUnit v3 Microsoft Testing Platform runner rejects. Running test projects directly with `dotnet run --project <test-project> --no-build` works.

## Code Coverage

- The 90% threshold applies to the merged report, which excludes the vendored `BrilliantMessaging.GuardClauses.g.cs` export. That file is generated by `scripts/generate-guard-clauses.sh`, is never edited by hand, and only a fraction of its assertions are reachable from our tests, so measuring it says nothing about this repository's test suite.
- Reproduce the CI numbers in two steps:
  1. `dotnet test BrilliantMessaging.slnx --configuration Release --no-build --results-directory artifacts/test-results --coverage --coverage-output-format cobertura`
  2. `reportgenerator "-reports:artifacts/test-results/**/*.cobertura.xml" "-targetdir:artifacts/coverage" "-reporttypes:Cobertura;MarkdownSummaryGithub" "-filefilters:-**/BrilliantMessaging.GuardClauses.g.cs"`
- Do not pass `--coverage-settings` to `dotnet test`. The option is accepted when a test project is launched directly with `dotnet run`, but under `dotnet test` it makes every test project report "Zero tests ran" (exit code 5). This is why the exclusion lives in the ReportGenerator step instead of a code coverage settings file.
